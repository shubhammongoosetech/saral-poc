## 2. Priority 1 — NIST P-256 Finite Field & Curve Arithmetic Audit

### 2.1 Distinction Between Base Field Prime $P$ and Subgroup Order $N$
In elliptic curve cryptography over Weierstrass curves, two distinct large primes govern operations:
1. **Base Field Prime $P$:** The characteristic of the finite field $\mathbb{F}_P$ over which the curve coordinates $(X, Y)$ are defined ($y^2 \equiv x^3 - 3x + b \pmod P$).
2. **Subgroup Prime Order $N$:** The number of points in the prime-order subgroup generated by the base point $G$ ($N \cdot G = \mathcal{O}$). All scalar arithmetic—including secret shares, polynomial coefficients, blinding factors, and private keys—must be conducted strictly modulo $N$ ($\mathbb{Z}_N$).

#### Standard NIST P-256 Constants
$$\begin{aligned}
P &= 2^{256} - 2^{224} + 2^{192} + 2^{96} - 1 \\
  &= \text{\texttt{0xFFFFFFFF00000001000000000000000000000000FFFFFFFFFFFFFFFFFFFFFFFF}} \\
N &= 2^{256} - 2^{224} + 2^{192} - 89188191079490199664194690199796956667 \\
  &= \text{\texttt{0xFFFFFFFF00000000FFFFFFFFFFFFFFFFBCE6FAADA7179E84F3B9CAC2FC632551}}
\end{aligned}$$

Notice that $P > N$.

#### Audit Findings in Code
- In `services/saral-node/cryptography/field.go`, the initialization logic correctly called `elliptic.P256().Params().N` to set `OrderQ`.
- However, line 14 contained a documentation comment error: `// q = 2^256 - 2^224 + 2^192 + 2^96 - 1`, which quoted the formula for $P$ while presenting the hex string for $N$.
- **Resolution Applied:**
  - Corrected the documentation in `field.go` to explicitly document both $N$ and $P$.
  - Exported `FieldP = new(big.Int).Set(curve.Params().P)` alongside `OrderQ` ($N$) to enforce rigorous mathematical boundaries in code and unit testing.

### 2.2 Canonical Scalar Encoding and Rejection Rules
As mandated by Cachin et al. and NIST SP 800-56A, non-canonical scalars ($\ge N$) must never be silently reduced via modulo; doing so introduces malleability vulnerabilities and invalidates commitment proofs.
- `NewFieldElementFromBigInt` rejects any scalar $b < 0$ or $b \ge N$ with `ErrInvalidScalarEncoding`.
- `NewFieldElementFromBytes` strictly rejects byte arrays whose length is not 32 bytes or whose big-endian value $\ge N$.
- **Test Evidence:**
  - `TestNISTP256OrderVsFieldPrime` verifies that passing $P$ as a scalar produces `ErrInvalidScalarEncoding` (since $P > N$).
  - Boundary test verifies that $N$ and $N+1$ are rejected.
  - Boundary test verifies that $N-1$ is accepted and exhibits the mathematical self-inverse property:
    $$(N - 1)^2 \equiv (-1)^2 \equiv 1 \pmod N \implies (N - 1)^{-1} \equiv N - 1 \pmod N$$

### 2.3 Constant-Time Assessment and Residual Side-Channel Bounds
1. **Elliptic Curve Operations:**
   In Go's standard library `crypto/elliptic`, `elliptic.P256()` utilizes specialized constant-time assembly routines (`p256_asm_amd64.s`, `p256_asm_arm64.s`) for point addition, point doubling, and scalar multiplication (`ScalarMult`). Scalar blinding and constant-time table lookups mitigate cache-timing and branch-prediction attacks.
2. **Byte Comparisons:**
   All equality checks on field elements and curve points utilize `crypto/subtle.ConstantTimeCompare`.
3. **Scalar Modular Arithmetic (`math/big`):**
   Go's `math/big.Int` is an arbitrary-precision integer implementation. Its internal branches depend on word slice lengths and sign bits.
   *Security Boundary:* In SARAL V3, all secret shares are uniformly distributed in $[1, N-1]$ via rejection sampling (`RandScalar`), ensuring 256-bit full-word representations. However, `math/big.Int` does not offer formal constant-time guarantees at the instruction level. A fully side-channel-free implementation would necessitate a dedicated Montgomery-arithmetic constant-time library (e.g., `fiat-crypto` or `subtle/p256`). For network-delivered asynchronous Byzantine consensus, timing variations are dominated by network latency ($>1$ ms), but physical local co-tenancy side-channels remain a documented bound.

## 3. Priority 2 — Asynchronous Validated Byzantine Agreement (ABBA / CKS00 / CKS05)

### 3.1 Vulnerability in Deterministic Reliable Broadcast
The previous implementation of `proactive/agreement.go` utilized Bracha's Reliable Broadcast (RBC) directly as an agreement protocol. While Bracha RBC ensures agreement on a single dealer's message, it does **not** solve Multi-Valued Byzantine Agreement when multiple nodes propose conflicting valid sets.
Under the Fischer-Lynch-Paterson (FLP) impossibility result, no deterministic asynchronous consensus protocol can guarantee termination in the presence of even a single crash fault. If node $P_1$ proposes valid set $S_1$ and node $P_2$ proposes valid set $S_2$, an asynchronous network scheduler can delay messages such that neither proposal achieves the $n-t$ threshold, resulting in permanent deadlock.

### 3.2 Implemented Randomized ABBA Architecture
To resolve the FLP deadlock without introducing trusted third parties or coordinators, SARAL V3 implements a full **Randomized Validated Asynchronous Byzantine Agreement (ABBA)** protocol grounded in **Cachin, Kursawe, Shoup (CKS00 / CKS05)** and **Cachin et al. (CCS 2002, Section 4)**.

```
       [ Proposal Dispersal (VRBC) ]
                     │
                     ▼
             [ Round r = 1, 2, ... ]
                     │
           Step 1: PRE-VOTE(r)
      (Leader L_r / Deterministic Choice)
                     │
        Collect >= n - t PRE-VOTEs
                     │
                     ▼
          Step 2: MAIN-VOTE(r)
        (Accept / Reject / Abstain)
                     │
        Collect >= n - t MAIN-VOTEs
          ┌──────────┴──────────┐
          │ >= 2t+1 Accept?     │ Split Votes?
          ▼                     ▼
     [ DECIDE S* ]      [ Query Common Coin ]
                        Exchange CoinShares
                                │
                      Collect >= t+1 Valid Shares
                                │
                        [ Combine Coin ]
                        Round Bit b_r in {0, 1}
                                │
                        b_r == 1: Lock Leading Candidate
                        b_r == 0: Rotate to Leader L_{r+1}
                                │
                                ▼
                       [ Start Round r + 1 ]
```

### 3.3 Verifiable Threshold Common Coin Construction over NIST P-256
The common coin provides an unpredictable, non-manipulable, verifiable random bit $b_r \in \{0, 1\}$ to break consensus symmetry in expected $O(1)$ rounds.

1. **Threshold Key Setup:**
   A master coin secret key $sk \in \mathbb{Z}_N$ is shared among committee participants using $(t+1)$-of-$n$ Shamir secret sharing:
   $$sk_i = P_{coin}(i) \pmod N, \quad PK_i = sk_i \cdot G, \quad PK_{master} = sk \cdot G$$
2. **Transparent Hash-to-Curve:**
   For committee tag $\tau$ and round $r$, a deterministic session string $M = \tau \parallel \text{":round:"} \parallel r$ is mapped to a curve point $H \in E(\mathbb{F}_P)$ of order $N$ via trial-and-increment hash-to-curve (`HashToCurve`).
3. **Coin Share Generation with Chaum-Pedersen DLEQ Proof:**
   Participant $P_i$ computes its coin share:
   $$\sigma_i = sk_i \cdot H$$
   To prevent Byzantine participants from injecting arbitrary curve points, $P_i$ attaches a non-interactive Zero-Knowledge Chaum-Pedersen proof $\pi = (c, z)$ proving:
   $$\log_G(PK_i) = \log_H(\sigma_i) = sk_i$$
   The verifier validates:
   $$\begin{aligned}
   R_1' &= z \cdot G - c \cdot PK_i \\
   R_2' &= z \cdot H - c \cdot \sigma_i \\
   c' &= \text{SHA-256}(G \parallel PK_i \parallel H \parallel \sigma_i \parallel R_1' \parallel R_2') \pmod N \quad (\text{verify } c' = c)
   \end{aligned}$$
4. **Lagrange Exponent Reconstruction:**
   Upon collecting any subset $T$ of $\ge t+1$ valid coin shares, nodes reconstruct the unique master point:
   $$\Sigma = \sum_{j \in T} \lambda_j(0) \cdot \sigma_j = \sum_{j \in T} \lambda_j(0) \cdot (sk_j \cdot H) = sk \cdot H$$
   Because $\Sigma$ is invariant to the choice of subset $T$, all honest nodes reconstruct the **exact same curve point**.
5. **Coin Bit Extraction:**
   $$b_r = \text{SHA-256}(\Sigma \parallel r)[0] \pmod 2$$
   Until at least one honest participant releases its share, the Byzantine adversary possesses at most $t$ shares and has zero information regarding $b_r$.

### 3.4 Byzantine Fault Tolerance Proof
- **Agreement (Safety):** Decision requires $\ge 2t+1$ `MAIN-VOTE(Accept)` messages. In an $n$-node committee with $n \ge 3t+1$, any two quorums of size $n-t$ intersect in at least $(n-t) + (2t+1) - n = t+1$ nodes. Because Byzantine nodes number at most $t$, at least one honest node is in the intersection and voted `Accept`. No conflicting proposal can ever obtain $2t+1$ votes.
- **Validity:** An honest node only votes `Accept` for proposal $S$ if $Q(S) = \text{true}$ (verifying $|S| \ge 2t+1$ and $C^{(d)}_{0,0} = Q_d$ for all dealers in $S$). Invalid proposals receive zero votes from honest nodes and can never be decided.
- **Termination (Liveness):** In rounds with split votes, the common coin outputs $b_r = 1$ with probability $1/2$, causing all honest nodes to adopt the leading plurality candidate in round $r+1$. All honest nodes vote identically in round $r+1$, deciding with probability 1. Expected rounds to termination: $\le 2$.

## 5. Physical & Runtime Limitations of Secure Erasure

### 5.1 In-Place Cryptographic Zeroing Implementation
`services/saral-node/vault/share_store.go` implements proactive secure erasure via:
1. Re-opening the target epoch JSON file with `os.O_WRONLY`.
2. Overwriting the plaintext with cryptographically secure random noise from `crypto/rand`.
3. Overwriting the file entirely with zero bytes (`0x00`).
4. Invoking `file.Sync()` (`fsync` syscall) to force flush of drive controller write buffers.
5. Unlinking the file with `os.Remove`.

### 5.2 Real-World Storage Limitations (Residual Risk)
While `SecureEraseEpoch` performs the maximum operation supported by OS syscalls, physical media and virtualization introduce bounds that software alone cannot eliminate:
1. **SSD Flash Wear-Leveling and Garbage Collection:**  
   Solid-State Drives (SSDs) and NVMe drives employ Flash Translation Layers (FTL). In-place block overwrites allocate new physical NAND flash blocks while queuing old blocks for background garbage collection. Plaintext remnants may linger in uncollected physical blocks until overwritten by drive firmware.
2. **Copy-on-Write (COW) Filesystems:**  
   Filesystems such as ZFS, Btrfs, APFS, and WAFL do not overwrite data in-place; they write modifications to new blocks. Overwrite operations create new disk extents without touching previous extents.
3. **Docker Storage Drivers & Snapshots:**  
   Docker container layers using `overlay2` or volume mounts on snapshotting storage (e.g., LVM thin pools, cloud EBS snapshots) retain previous versions in snapshot blocks.
4. **Go Runtime Heap Copies:**  
   The Go memory allocator manages memory in arenas. When big integer objects (`*big.Int`) or strings are dereferenced, they become garbage-collection candidates. Until the GC cycles and the memory is reused or wiped, scalar bytes may reside in unzeroed heap space.

*Security Recommendation for Production:* Use dedicated hardware security modules (HSM) or Linux `tmpfs` RAM-disks with `mlock` to host volatile node share stores, and disable swap space (`swapoff -a`).

## 7. Remaining Limitations & Production Roadmap

1. **Hardware-Enforced Memory Zeroing:**
   Replace heap-allocated `big.Int` share representations with explicit fixed-size byte buffers that invoke `memguard` or `mlock` to eliminate garbage-collector memory retention.
2. **Mechanized Formal Proofs:**
   Construct machine-checked proofs in EasyCrypt or Coq for the finite-state machine transitions of `services/saral-node/proactive/agreement.go`.
3. **DKG / TSS / Wallet Separation:**
   As specified in the operational guidelines, Distributed Key Generation (DKG) and Threshold Signature Scheme (TSS) transaction signing layers remain strictly decoupled and are not implemented here.
