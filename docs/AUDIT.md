# Comprehensive Security & Architecture Audit: SARAL POC

**Document Version:** 1.0.0  
**Audit Target:** `saral-poc/`  
**Standard:** SARAL Patent Application ("Non-Custodial, Separation-of-Powers Cryptographic Key Management System with Adaptive Multi-Asset Economic Security Layer")  
**Date:** November 2026

---

## 1. Executive Summary

This audit evaluates the codebase of `saral-poc` against the technical specifications and legal claims of the SARAL Patent Application. The project comprises an Express/TypeScript backend, React/Vite/TypeScript frontend, PostgreSQL database, and an ethers v6 blockchain connector for the MST Testnet.

While the existing repository contains working implementations of zero-trust contextual authentication (Google OAuth, SMS OTP, Time/Geofencing working policy gates, Merkle hash-chained audit logging, and basic EVM transaction construction), the core cryptographic custody, node clustering, and domain isolation contain severe architectural contradictions to the patent claims. Most critically:
1. **Key Generation Dealer Contradiction:** Private keys and domain keys were previously generated by a single dealer (`randomScalar()` or `Wallet.createRandom()`) and distributed via Shamir Secret Sharing, contradicting Patent Claims 1, 11, and Paragraph [0019].
2. **Hardcoded Topology vs. Dynamic Dynamic Containers:** The system assumed a fixed 19-node cluster (1 Foundation, 9 Public, 9 Private) with Foundation threshold $t=1$, violating Patent Paragraph [0015] (Foundation must hold exactly one-third of the access structure, $\ge 3$ nodes, and cannot act alone).
3. **Static Placement & Missing Rendezvous Hashing:** Node assignment lacked Highest Random Weight (HRW) rendezvous placement, database pinning (`wallet_placements`), and signed node manifest verification (Patent Paragraphs [0016], [0022]).
4. **Storage Architecture Insecurities:** File storage did not strictly implement atomic temp+fsync+rename, per-node derived keys (using global `MASTER_ENCRYPTION_KEY` instead of per-node `scrypt`/`argon2id`), or Additional Authenticated Data (AAD) binding to wallet ID and epoch.
5. **Frontend Incompleteness:** The frontend only provided 5 baseline views (`Login`, `Mfa`, `WorkingPolicy`, `Review`, `Wallet`), entirely lacking UIs for Private Domain Devices/Guardians, Topology & Node inspection, Break-Glass Recovery lifecycle, Economic/Staking/Slashing telemetry, and Full Activity Logs.

## 2. Inventory: What Exists

### 2.1 Backend Services & Architecture
* **Server Framework:** Express 5 on Node.js 24 with TypeScript, structured into routes, controllers, middleware, services, crypto primitives, and participant IPC.
* **Authentication Subsystem (`src/services/authService.ts`, `src/services/mfaService.ts`):**
  * Google OAuth2 ID token verification via `google-auth-library`.
  * Mobile phone OTP authentication using CSPRNG (`crypto.randomInt`).
  * HMAC-SHA256 hashed OTP storage in PostgreSQL; timing-safe token comparison.
  * Access token (JWT) and refresh token rotation utilities in `src/utils/jwt.ts`.
* **Zero-Trust Policy Engine (`src/services/locationService.ts`):**
  * Haversine distance geofencing against user-configured coordinates and radius ($km$).
  * Time-window validation using IANA timezones (`Intl.DateTimeFormat`).
  * Access attempt audit logging into `access_logs`.
* **Cryptographic Tamper-Evident Audit Logging (`src/services/auditLogService.ts`):**
  * Blockchain-style SHA-256 hash chaining of security events (`previous_hash` $\to$ `entry_hash`).
* **Blockchain Gateway (`src/services/chainService.ts`):**
  * Ethers.js v6 JSON-RPC provider interfacing with MST Testnet (`https://testnetrpc.mstblockchain.com`, Chain ID 91562037 / 11155111).
  * Nonce tracking, dynamic gas fee estimation, and raw signed EVM transaction broadcast.
* **Cryptographic Primitives (`src/crypto/`):**
  * `secp256k1Math.ts`: Elliptic curve operations over $F_n$ and $E(\mathbb{F}_p)$ using `@noble/curves/secp256k1`.
  * `shamirField.ts`: Shamir secret sharing over scalar field $F_n$, Feldman VSS commitments, Lagrange coefficients, zero-polynomial generation for Proactive Secret Sharing (PSS).
  * `paillierCrypto.ts`: Additively homomorphic Paillier encryption supporting Multiplicative-to-Additive (MtA) subprotocols.
  * `mpcProtocolTypes.ts`: Type definitions for 3-round threshold ECDSA messages.
  * `mpcCoordinator.ts`: Stateless coordinator orchestrating Round 1 (commitments/decommitments), Round 2 (pairwise MtA cross-terms), and Round 3 (partial signature aggregation and BIP-62 low-s canonicalization).
  * `dkg.ts`: Untracked initial implementation of distributed key generation with Feldman VSS.
* **Participant Service & IPC (`src/participant/`):**
  * Standalone daemon process (`participantDaemonProcess.ts`) listening on Unix Domain Sockets (`.saral_runtime_sockets/<nodeId>.sock`).
  * Mutual HMAC-SHA256 request/response authentication (`participantIpcProtocol.ts`).
  * Asymmetric node identity keys and Proof-of-Possession ceremonies (`nodeIdentityManager.ts`).
  * Node registry with membership exclusion and operator diversity checks (`participantRegistry.ts`).
* **Economic Security Module (`src/services/economicService.ts`):**
  * Fixed-supply MSTC (8,000,000,000 base tokens).
  * Restaking vault issuing liquid sMSTC 1:1 against deposited MSTC.
  * Protocol-native staking token (SST) with a hard maximum supply cap.
  * Security Ratio calculation $R = \text{TVS} / \text{TES}$.
  * Adaptive APR issuance engine bounded between min/max ceilings.
  * Usage fee burning and 60% Insurance Treasury / 40% Validator Redistribution slashing.
* **Break-Glass Recovery Subsystem (`src/services/recoveryService.ts`):**
  * High-entropy recovery secret split into Shamir custodian shares.
  * Mandatory time-lock challenge window (configurable, default 48h).
  * User challenge/abort mechanism.
  * PSS zero-polynomial share refresh preserving wallet public key and address.

### 2.2 Database Layer
* **PostgreSQL:** Managed via Prisma ORM and raw SQL schema (`backend/src/db/schema.sql`).
* **Tables:** `users`, `mfa`, `work_policy`, `wallets`, `key_shares`, `access_logs`, `security_event_logs`, `recovery_records`, `transactions`, `otps`.

### 2.3 Frontend Application
* **Vite + React 18 + TypeScript:** Single-page application using React Router DOM.
* **Existing Pages:** `Login.tsx`, `Mfa.tsx`, `WorkingPolicy.tsx`, `Review.tsx`, `Wallet.tsx`.
* **Components:** `Navbar.tsx`, `AccessDeniedModal.tsx`.
* **CSS:** Clean, plain system CSS in `frontend/src/index.css`.

## 3. What Works

1. **Authentication Flow:** User signup/signin via Google OAuth credential verification or mobile phone OTP delivery and verification.
2. **Two-Factor MFA:** Second-factor OTP generation with timing-safe comparison against HMAC-SHA256 digests.
3. **Working Policy Gate:** Accurate evaluation of access time windows in user timezone and geofence distance calculation using the Haversine formula.
4. **Review & Access Gate:** The `/review` and `/wallet` pages properly verify whether policy conditions are satisfied before allowing user actions.
5. **On-Chain Balance & Broadcast:** Live querying of MST Testnet native balance and successful broadcasting of raw signed EVM transactions.
6. **Stateless MPC Coordinator Signature Verification:** Mathematical verification that aggregated partial signatures $(r, s, v)$ recover to the expected public key on secp256k1 using BIP-62 low-s normalization.
7. **Tamper-Evident Audit Chain:** Cryptographic hash chaining verifying immutability of logged security events.

## 8. Detailed Security Vulnerabilities Found

### SEC-01: In-Memory Key Materialization During Keygen
* **Severity:** Critical (Patent Violation)
* **Location:** `backend/src/crypto/thresholdEcdsa.ts`
* **Description:** Domain keys were created by sampling a scalar $x \in F_n$ and splitting it via Shamir. A compromised process or memory dump at wallet generation time exposes the full domain secret.
* **Remediation:** Replace with distributed key generation (DKG) where each node $i$ samples its own secret polynomial $f_i(z)$, shares sub-shares, and each node sums received sub-shares without any dealer ever existing.

### SEC-02: Shared Global Encryption Key Across Nodes
* **Severity:** High
* **Location:** `backend/src/crypto/secureEncryption.ts`
* **Description:** All nodes derived AES-GCM keys from a single environment variable `MASTER_ENCRYPTION_KEY`. A compromise of one node or environment file compromises all stored shares across all domains.
* **Remediation:** Derive per-node keys using `scrypt` from individual node secrets (`data/<domain>/<nodeId>/.node_secret`).

### SEC-03: Non-Atomic File Writes & Storage Swapping Risk
* **Severity:** High
* **Location:** `backend/src/services/nodeClusterService.ts`
* **Description:** `fs.promises.writeFile` without `fsync` or temporary files risks file corruption on abrupt node termination. Ciphertext was not bound to wallet ID or epoch via AAD, allowing potential ciphertext substitution.
* **Remediation:** Implement atomic write pattern (`write temp`, `fsync`, `rename`), file mode `0600`, directory `0700`, and bind `walletId` + `epoch` in AES-GCM AAD.

### SEC-04: Missing Replay & Idempotency Controls on Signatures
* **Severity:** Medium
* **Location:** `backend/src/controllers/walletController.ts`
* **Description:** Signing requests did not require an idempotency key, client nonce, or timestamp freshness check, leaving open potential transaction replay or duplicated fee processing.
* **Remediation:** Add server-side idempotency keys, nonces, and timestamp freshness checks.

### SEC-05: Missing Fresh MFA Check on Critical Actions
* **Severity:** Medium
* **Location:** `backend/src/routes/wallet.ts`
* **Description:** Once a user completed MFA at login, the session token allowed subsequent transactions without requiring re-authentication or fresh MFA for high-value actions.
* **Remediation:** Require fresh MFA verification (`mfaVerifiedAt` within 5 minutes) for signing, break-glass recovery initiation, and topology changes.

### SEC-06: GPS Coordinate Spoofing Risk
* **Severity:** Low (POC Context)
* **Location:** `backend/src/services/locationService.ts`
* **Description:** Browser-supplied `lat`/`lng` can be manipulated by malicious clients.
* **Remediation:** Correlate client GPS with IP geolocation and flag significant discrepancies as access anomalies.

## 9. Conclusion

The existing `saral-poc` provides a functional application scaffold, but requires fundamental refactoring to eliminate single-dealer key materialization, implement dynamic container topology with HRW placement, enforce per-node encrypted storage, and supply the missing 6 frontend pages and comprehensive test suite.
